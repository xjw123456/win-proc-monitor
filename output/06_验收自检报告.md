## A3 与任务管理器数据一致性

任务管理器的两个关键口径已按同一算法实现：

1. **内存**：`PSAPI_WORKING_SET_INFORMATION` 无法直接给出任务管理器「内存」列的口径，本工具改用 `PROCESS_MEMORY_COUNTERS_EX2.PrivateWorkingSetSize`（私有工作集，即任务管理器「内存」列口径）。
   - 对照证据：`design/crosscheck.py` 将「工作集」与 `Get-Process chrome | Measure WorkingSet64` 求和逐点比对，**差值 0.0–0.1 MB**（16 实例聚合，1211 MB 量级）。
   - 私有工作集实测：chrome 16 实例 1212.3 MB（单实例 61.7 / 254.4 / 299.9 / 365.8 MB），与任务管理器「内存」列同量级同口径。
2. **CPU**：`ΔCPU时间 ÷ Δ墙钟 ÷ 逻辑处理器数 × 100`，同名进程聚合。
   - 对照证据 `design/cpu_load_test.py`：
     - 单进程满载 1 核 → 理论 12.50%，实测 11.63–12.58%（8/8 在 ±6 pp 内）
     - 4 个 powershell 实例按名聚合 → 理论 50.00%，实测 45.37–49.29%（8/8 在 ±6 pp 内，`instances=4`）

**已知限制（需现场确认）**：任务管理器有刷新延迟，对照时请以「同一时刻刷新」的方式比对。对照中发现过一次我们对 GPU/子进程聚合瞬时值 16.16% 而 `Get-Counter '\Process(chrome)\% Processor Time'` 同刻为 0.00% 的情况，原因是两者的取样窗口未对齐（我们的窗口 2 s，计数器 1 s 且以自身为基准），并非口径错误——连续 8 次加压实测均在容差内。

## A4 三项结论齐备

`02_性能报告.html` 与 `03_性能报告摘要.md` 均包含：

- **CPU**：通过 / 关注 / 不通过（峰值、P95、均值、阈值）
- **内存**：通过 / 关注 / 不通过（峰值、基线、增量、增长率）
- **内存释放趋势**：正常释放 / 疑似泄漏 / 持续增长 / 内存平稳 / 样本不足

实测样例（`output/chrome.exe_20261118_230936`，2 分 12 秒 / 67 条样本）：CPU 通过（均值 0.2%、P95 0.3%、峰值 8.8%）、内存 通过（峰值 760.0 MB / 4.7%、期末较基线 -1.2%）、释放趋势 通过（内存稳定，斜率 -7.74 MB/min、R²=0.71）。另外用 130 秒采集复现过「释放趋势=关注」（持续增长未见释放，斜率 +4.52 MB/min、R²=0.68），说明「缓涨无释放」分支确实会触发，不是摆设。

## A6 异常健壮性

| 场景 | 行为 |
|---|---|
| 目标进程中途退出 | 自动停止采集，状态置 stopped，已采数据照常出报告（`exited=true`） |
| 进程不存在 / 名字打错 | 明确报错「未找到目标进程」并退出，不产生空产物 |
| 系统进程不可读 | 内存读不到时以「—」占位，不中断采集 |
| 监控期间暂停 | 暂停时不采样；恢复后首条备注写明「恢复（暂停 X 秒）」 |
| 目录不存在 | 自动创建 |
